# OpenAPI Generator Rust Reqwless Library (sub-template)


## Overview

This is a an OpenAPI genenerator library, also called a sub-template,
for the Rust reqwless HTTP client library.

reqwless is a Rust HTTP client for embedded devices.  It can be used
in a no_std environment.  Rust standard library modules like String
and Vec are not supported.  It instead uses string slices or the
heapless library's String and Vec implementation.

Other than that, it shares many API similarities with the Rust reqwest
crate.  Because of this, the OpenAPI Generator Rust reqwest library
was used as the basis for this library.

## Implementation

This Rust generator library is similar to the reqwest library
implementation.  It adds a subdirectory to the
`modules/openapi-generator/src/main/resources/rust` directory called
reqwless that contains reqwless specific code.  In addition, it
modifies some common files in the rust directory such as the Cargo
mustache template (`Cargo.mustache`), top-level lib crate
(`lib.mustache`) and model source (`model.mustache`).

In addition, it adds the reqwless library to the list of Rust
libraries in `RustClientCodegen.java`.

Most of the x-vendor-extension information was available by default in
the needed Mustache template sections.  But the response section
needed to be modified to make lifetime information available.

So the `RustClientCodegen.java` `handleMethodResponse` moethod was
modified to include response lifetime information in the
`op.vendorExtensions` map object, which makes it available to mustache
templates, in particular the `api.mustache` template.

`api.mustache` is where most of the reqwless generation logic is
included.

It currently does not support many features required for
enterprise-level applications.  It has no support for AWS tokens or
Google tokens or more complex authentication methods.  Interested
parties are welcome to contribute patches for those features or create
a new fork.  I'm sure there are happy engineers, project managers and
organizations who would love to estimate time required, drive the
process and commit resources.

## Differences with reqwest generator library

There are some incompatible API differences between reqwest and
reqwless that can't be easily fixed without deeper changes.  This
includes the headers methods on the RequestBuilder trait and the
header fields on the Request structures.  They use a key-value map to
set and retrieve header entries.  The key-value map relies on the
Hyperium http crate which uses the standard library HashMap module,
which is not available in no_std.

Because standard library String and Vec aren't supported in the
reqless library, either the heapless implementation needs to be used
or string slices need to be used.

All the heapless data structures have a type parameter to specify
their capacity.  So instead of a standard library Vec of u8 unsigned
integers:

`let my_vec: std::Vec<u8> = std::Vec::new();`

You would use the following:

`let my_vec: heapless::Vec<u8, 8> = heapless::Vec::new();`

## Lifetimes and Lifetime OpenAPI Vendor Extensions

We can also use references, and let the higher-level client manage the
underlying data, either with a static data store and pool of objects
or something else.

If references are used, then lifetimes need to be specified for most
common use-cases.  This document describes how OpenAPI Schemas can be
augmented to describe lifetime relationships between schemas,
operations and operation responses.

This OpenAPI Generator library also simple string slices with lifetime
parameters.

Here is an example model generated by the reqwless generator with
string slices:

```
#[derive(Clone, Default, Debug, PartialEq, Serialize, Deserialize)]
pub struct Book<'book> {
    #[serde(rename = "id")]
    pub id: i32,
    #[serde(rename = "title")]
    pub title: &'book str,
```

But lifetime parameters need to be specified for functions and other
data structures and types that use these data structures.  To support
this, either the OpenAPI Generator Rust codegen modules need to
determine lifetimes automatically or they need to be specified by the
OpenAPI schema author.

This library supports the second option.  It uses a set of OpenAPI
vendor extensions that users need to add to their OpenAPI schema to
guide the code generation process.

Because Rust is not the only possible language with lifetimes, these
were not implemented as "langauge-specified vendor extensions",
i.e. they dont't use the `x-rust-{extension-name}` form.

The following extensions have been added to help schema authors:

- `x-regions-lifetimes`
- `x-regions-generic-type-parameters`
- `x-regions-trait-bounds`
- `x-regions-is-reference`
- `x-regions-lifetime`

There is one Rust specific extension to indicate whether code should
NOT be generated for the standard library:

- `x-rust-no-std`

Below each vendor extension is described

### `x-regions-lifetimes`

Lifetimes constraints can be added to individual schemas, operations
and operation responses.

The `x-regions-lifetimes` vendor extension can be added to the following
OpenAPI sections:

- individual schema objects
- operations
- responses objects

#### `x-regions-lifetimes` for individual schema objects

For individual schema objects, the `x-regions-lifetimes` field contains a list
that indicates that the object (usually a struct in Rust) can't
outlive the fields with the corresponding lifetimes.  Those field
lifetimes are annotated with the `x-regions-lifetime` vendor
extension.

The snippet below from the example schema shows the use of
`x-regions-lifetimes` in the Book schema object.  It indicates that Book
object cannot outlive the title or pub_date references passed in.

```
components:
  schemas:
    Book:
      type: object
      x-regions-lifetimes: [book, dt]
      properties:
        id:
          type: integer
          readOnly: true
        title:
          type: string
          maxLength: 200
          x-regions-is-reference: true
          x-regions-lifetime: book
        pub_date:
          type: string
          format: date-time
          title: Date published
          x-regions-is-reference: true
          # This doesn't need to be a different lifetime than 'book,
          # but I wanted to test the ability to have multiple
          # lifetimes in a single model.
          x-regions-lifetime: dt
      required:
      - id
      - pub_date
      - title
```

#### `x-regions-lifetimes` for operations

Operations can contain multiple constraints and type parameters:
lifetimes, generic type parameters and trait bounds.  Each one is used
to specify constraints for a different part of the operation.

Operations can return objects in addition to response codes.  For
example, a list of items in a `get` without a parameter, or a single
object in a `get` with an `ID` parameter.

`x-regions-lifetimes` in operations indicates how long those response items
can live in relation to the other operation parameters.

Operations naturally translate to Rust functions.  `x-regions-lifetimes` in
operations specifications add lifetime annotations to the function
return signatures and specify how long the returned reference of the
function should live in relation the the operation (function)
parameters.

For operations, the `x-regions-lifetimes` field contains a list that indicates
that the returned reference (usually a struct or Vec of structs in
Rust) should live as long as the parameters with corresponding
lifetimes annotations.

The snippet below from the example schema shows the use of
`x-regions-lifetimes` in the `get` operation.

```
  /books/{id}/:
    get:
      operationId: books_retrieve
      description: API endpoint that allows books to be viewed or edited.
      x-regions-lifetimes: [client, response]
      x-regions-generic-type-parameters: ["'book", "'dt",  "'client", "'response", "T", "D"]
      x-regions-trait-bounds:
        - "'client: 'response"
        - "'client: 'book"
        - "'client: 'dt"
      parameters:
      - in: path
        name: id
        schema:
          type: integer
        description: A unique integer value identifying this book.
        required: true
      tags:
      - books
      security:
      - cookieAuth: []
      - basicAuth: []
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Book'
          description: ''
          x-regions-lifetimes: [book, dt]
```

### `x-regions-generic-type-parameters`

`x-regions-generic-type-parameters` specifies any generic type parameters,

the union of every lifetime in the response and parameters.

The `x-regions-generic-type-parameters` vendor extension can be added to the
following OpenAPI sections:

- operations

#### `x-regions-generic-type-parameters` for operations

### `x-regions-trait-bounds`

Trait bounds are used to specify more specific lifetime relationships
in operations. Simple use cases will have the entire model object live
as long as every parameter.  But sometimes we want to specify more
limited lifetimes between individual objects, or just group lifetimes
to more easily understand the expected behavior.


- operations

#### `x-regions-trait-bounds` for operations

### `x-regions-is-reference`

`x-regions-is-reference` is a vendor extension that is a boolean
value (true or false), that indicates whether a structure field is a
reference or not.

The `x-regions-is-reference` vendor extension can be added to the
following OpenAPI sections:

- individual schema object properties

#### `x-regions-is-reference` for individual schema object properties

`x-regions-is-reference` is a vendor extension that is a boolean
value (true or false), that indicates whether a structure field is a
reference or not.  If you set this extension to true, field types will
be generated that are references.  For example, for the title field
the following schema:

```
        title:
          type: string
          maxLength: 200
          x-regions-is-reference: true
          x-regions-lifetime: book
```

Will generate this field: `pub title: &'book str`


### `x-regions-lifetime`

The `x-regions-lifetime` vendor extension can be added to the
following OpenAPI sections:

- individual schema object properties

#### `x-regions-lifetime` for individual schema object properties

`x-regions-lifetime` is added to schema object properties (which
generate Rust struct fields) to indicate that a field has a specific
lifetime.  The structure can then contain a `x-regions-lifetimes` vendor
extension with the same lifetime name that indicates the structure
can't outlive the field.
